## Defects (failing tests left in place; severity QA's assessment)
### D1 — Order totals do not equal the approved quote document when a line has a discount (Medium)
- **Test**: `apps/api/tests/qa/test_qa_stage3_orders.py::test_order_totals_equal_the_approved_quote_document_with_line_discount`
- **Where**: `apps/api/app/services/intelligence/orders.py:130` folds the discount into `unit_price` (`ln.unit_price * (1 − discount_pct/100)` = 0.78625) and `recompute_totals` (`orders.py:66-78`) rounds `qty × unit_price` once; the approved quote (`services/pricing.py::compute_line`) rounds subtotal and discount separately (425.00 − 31.88).
- **Request**: `PATCH /quotes/{id}` `{lines:[{id, discount_pct:"7.5"}]}` on the one-line quote (500 × 0.85 AED, tax 5 %) → submit → approve → `POST /quotes/{id}/orders {}`.
- **Expected**: order `subtotal` 393.12, `tax_total` 19.66, `grand_total` 412.78 (the figures the approver and customer saw).
- **Actual**: `subtotal` 393.13 (500 × 0.78625 = 393.125 → HALF_UP), `grand_total` 412.79; the order also shows a unit price (0.78625) that appears nowhere on the approved document. Violates "prices are copied from the approved document — never recomputed" (S3-F02, `orders.py` docstring) and Stage 1's per-line rounding fixture (S1-A12).

### D2 — `pending_value` KPI contradicts its own published definition (Medium)
- **Test**: `apps/api/tests/qa/test_qa_stage3_kpis.py::test_pending_value_includes_every_open_approved_quote_per_its_definition`
- **Where**: `apps/api/app/services/intelligence/kpis.py:97` selects `Quote.status == "approved"` only; `kpis.py:33-37` defines the metric as approved quotes "still open (not won, lost, withdrawn or expired)". Quotes moved to `sent`, `acknowledged` or `awaiting_customer` (Stage 2 lifecycle, `services/lifecycle.py`) change `quote.status` and silently drop out of the pipeline value.
- **Request**: two approved one-line quotes (446.25 AED each); `POST /quotes/{id}/transition {to_status:"sent"}` on one; `GET /kpis`.
- **Expected**: `pending_value = {count: 2, value: "892.50"}`.
- **Actual**: `{count: 1, value: "446.25"}` — the dashboard under-reports open pipeline as soon as sales does its job (S3-A01 "KPIs match fixtures", PRD "metrics must have clear definitions").

### D3 — Orders CSV import crashes with HTTP 500 on an over-long cell instead of rejecting the row (Medium)
- **Test**: `apps/api/tests/qa/test_qa_stage3_data_io.py::test_oversized_field_values_are_rejected_per_row_not_as_a_crash`
- **Where**: `apps/api/app/services/intelligence/data_io.py:244-301` validates numbers and currency per row but not string lengths; `orders.py:195` writes `unit` (column `VARCHAR(16)`) and `external_ref` (`VARCHAR(100)`) unchecked; the `begin_nested()` at `data_io.py:290` does not catch `DataError`, so the exception escapes the request.
- **Request**: `POST /data/import/orders?idempotency_key=big-fields` with rows `PO-OK` (valid), `PO-UNIT` (`unit = CARTONS_OF_TWELVE_PIECES`, 24 chars) and an `order_ref` of 123 chars.
- **Expected**: 201, `applied 1, rejected 2`, both bad rows in `report.failed_rows` with a reason (S3-A07 partial-import recovery, API_CONTRACT "per-row validation, partial apply").
- **Actual**: HTTP 500 (`psycopg.errors.StringDataRightTruncation: value too long for type character varying(16)`, logged as "unhandled error"); the whole request rolls back, so the valid `PO-OK` order is not created and no `sync_runs` row exists for the operator to see. The same unvalidated path is used by `connectors._sync_orders` (`connectors.py:396-416`) and by `_sync_products` apply_remote for `unit`. Overlaps the auditor's SEC3-04 (xfail tests in `tests/security/test_stage3_audit_inputs.py`).

### D4 — A customer whose deletion was approved still accepts new processing (Low)
- **Test**: `apps/api/tests/qa/test_qa_stage3_repeat_retention.py::test_approval_stops_processing_immediately_and_keeps_commercial_records`
- **Where**: `apps/api/app/api/routers/rfqs.py:113-119` (`_resolve_customer`) and `routers/followup.py:80-83` (contact creation) look the customer up without `deleted_at IS NULL`; only `/customers` list, exports, `order-proposals` and the data importer filter soft-deleted rows.
- **Request**: sales requests, admin approves deletion (customer hidden, contacts opted out, schedules cancelled — all verified); then `POST /rfqs {text, customer_id:<deleted>}` and `POST /customers/<deleted>/contacts`.
- **Expected**: 404/409 — the API contract states approval "soft-deletes immediately" and the subject is pending purge; new RFQs/quotes/contacts for it re-create personal data that the purge job does not know about (`retention.purge` deletes contacts/drafts and pseudonymises, but a quote/RFQ created after approval re-attaches the pseudonymised customer and may carry new `pasted_text`).
- **Actual**: `POST /rfqs` → **201** (RFQ created for the deletion-approved customer). `POST /customers/<deleted>/contacts` → **201** as well (new personal data attached to the deletion-approved subject). The security auditor reports the same area as SEC3-02 (`tests/security/test_stage3_audit.py`, xfail).

### D5 — Mutations answer 2xx before their transaction is committed (Medium; pre-existing since Stage 1, found in this run)
- **Tests**: `apps/api/tests/qa/test_qa_stage3_consistency.py::test_created_record_is_committed_when_the_201_is_sent`, `::test_order_confirmation_is_committed_when_the_200_is_sent` (deterministic: a second connection probes the database at the instant the final response byte is sent); live measurement R9; browser symptom R7c(a).
- **Where**: `apps/api/app/db/session.py:73-82` — `get_db` commits *after* `yield`. With the installed FastAPI 0.162.0 / Starlette 1.10.0 (pin `fastapi>=0.115` in `apps/api/pyproject.toml`) the exit code of a `yield` dependency runs after the response has been sent. The file is unchanged since Stage 1 (`git log -- apps/api/app/db/session.py`), so this is **not a Stage 3 regression**; it affects every mutating endpoint of all three stages.
- **Request**: `POST /customers {name}` → 201; `POST /orders/{id}/confirm` → 200 `status: confirmed`.
- **Expected**: when the success response is sent, the row (and its `audit_events` row — "within the same transaction") is committed.
- **Actual**: at response end the second connection sees 0 customer rows / `(confirmed rows, audit rows) = (0, 0)`. Against a real uvicorn, 3 of 400 immediate `GET /customers/{id}` after a 201 returned 404 (R9). In the browser a quote showed "Submitted for approval." with status *draft* and an enabled Submit button (R7c). Consequences: intermittent stale screens and flaky browser tests (the three R7a failures that passed in isolation fit this pattern, though that attribution is an inference), and — more seriously — a commit failure after the response can no longer be reported: the client has already been told the approval/confirmation/deletion succeeded.

## Observations (not defects, or below the bar for a failing test)
- O1 — Proposal `lines[].quantity` is serialised as `"500.000"` while every other money/quantity field is normalised (`"500"`); the UI copes but API consumers see two formats (`repeat_orders.analyse`).
- O2 — Within one approval transaction the audit rows are written `order.propose` → `order_proposal.approve` (the proposed order is created before the decision row). Chronology is still truthful; a reviewer reading the trail should expect this order.
- O3 — (also reported by the auditor as SEC3-06) Import idempotency is keyed per tenant irrespective of entity: re-using a customers key for an orders upload returns the customers run (201, `entity: customers`). Observed by code reading (`routers/intelligence.py::import_data`), not exercised; documenting the contract ("same key → same run") in the UI would avoid surprises.
- O4 — `profile.stats.last_order_at` takes the `confirmed_at` of the most recently *created* confirmed order, not the latest confirmation (`routers/intelligence.py::customer_profile`). Equal in all QA fixtures; differs when an older order is confirmed later.
- O5 — Customer import silently truncates `name` to 200 and `reference` to 100 characters instead of rejecting the row; `email` > 320 chars is rejected by `valid_email`. Same family as D3 but lossless for the import itself.
- O6 — Formula neutralisation prefixes `'` to values beginning with `- + = @`; a legitimately dashed value (e.g. a customer named "-Dash Co") therefore round-trips through failed-rows CSV → re-upload with a leading apostrophe. Acceptable security trade-off (CLAUDE.md), worth a note in the UI next to "Download failed rows".
- O7 — `GET /orders`, `/order-proposals`, `/sync-conflicts`, `/retention/requests` are capped at 200 rows with no pagination or `total`; a busy tenant cannot see older rows through the UI.
- O8 — The connector `products` sync counts an identical record as `applied` (a no-op). Correct but the word suggests a write; "unchanged" would be clearer in the run table.
- O9 — Browser `money()` prints no currency code (the implementer already adjusted the spec); the order and profile tables rely on the header/subtitle for the currency. Fine for single-currency tenants; a multi-currency customer list would be ambiguous.
- O10 — The implementer's `stage2-followup.spec.ts:66` opts out `getByTestId("opt-out").first()` on the first seed customer; it only works while that customer has no other eligible primary contact. Any other spec (or a second run on the same database) that adds one makes it fail (R7c(b)). Selecting the contact it just created would make it order-independent.
- O11 — Playwright runs do not reset the database (global-setup seeds idempotently), so data accumulates across runs on one database; QA ran the API suite (which truncates) between browser runs, which is why R7c/R7d started from a fresh seed.
