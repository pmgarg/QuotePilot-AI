## Defects
Severity uses the project scale: Critical = breaks a Stage 2 acceptance criterion with customer-facing harm; High = a functional requirement is violated with customer-facing effect; Medium = a requirement gap or reliability problem with a workaround; Low = minor.

### D-01 — Critical — opt-out can be bypassed by a second contact row with the same address (S2-A02)
- **Test:** `S:test_qa_s2_a02_opt_out_is_enforced_per_address_not_per_contact_row`
- **Steps:** sales `POST /customers/{c}/contacts {"email":"buyer@customer.example"}`, then `POST /contacts/{id}/opt-out {"opted_out":true}`, then `POST /customers/{c}/contacts {"email":"Buyer@Customer.example"}` (case variant), then admin enables automation, sales marks the quote sent, `POST /quotes/{q}/drafts {"contact_id":<dup>}`, send, and the worker runs.
- **Expected:** the opted-out address receives nothing; creating the duplicate or drafting for it is refused (403 `opt_out`).
- **Actual:** draft 201; **4 messages delivered** to `Buyer@Customer.example` (1 manual, 3 automated).
- **Where:** opt-out is stored and checked per `contacts` row: `service.py:345` (send gate), `:509` (planning), `:616` (worker); `routers/followup.py:76-99` creates a contact for an already opted-out address without checking. There is no address-level suppression list.

### D-02 — High — an unsubscribe reply opts out only one of the contact rows for that address (S2-F08, S2-A02)
- **Test:** `I:test_qa_s2_f08_unsubscribe_reply_opts_out_every_contact_row_with_that_address`
- **Steps:** two contacts `buyer@…` and `BUYER@…`; inbound "STOP - remove me…" from `buyer@…`.
- **Expected:** every row for the address is opted out. **Actual:** `BUYER@customer.example` stays subscribed.
- **Where:** `service.py:685-687` (`db.scalar(...)` picks one row); `:704-715`.

### D-03 — Critical — concurrent send clicks deliver the same draft multiple times (S2-A03)
- **Test:** `S:test_qa_s2_a03_concurrent_duplicate_sends_deliver_exactly_once`. Non-deterministic: failed in the first R4 attempt and in R6, passed in the final R4 run.
- **Steps:** 4 authorised users `POST /drafts/{id}/send` at the same time (thread pool).
- **Expected:** 1 provider message, 1 `sent` event, 1 `draft.sent` audit row. **Actual:** **4 provider messages** for one draft, all requests 200.
- **Where (probable root cause, inferred from code):** `service.py:321-332`. The `SELECT … FOR UPDATE` returns the instance the router already loaded into the session identity map (`routers/followup.py:312-320`, `_draft`). Without `populate_existing`, the attributes are not refreshed after the lock is granted, so the `status == "sent"` check at `:329` reads a stale `draft`.

### D-04 — High — a contact who prefers "no follow-ups" receives automated follow-ups (S2-F02, S2-A02)
- **Test:** `S:test_qa_s2_a02_contact_preferring_no_follow_ups_is_never_auto_messaged`
- **Steps:** contact with `preferred_channel:"none"` (offered in the UI as "no follow-ups"); automation enabled; mark sent; worker runs.
- **Expected:** no message. **Actual:** **3 automated messages** to `quiet@customer.example`.
- **Where:** `service.py:509` (planning) and `:616` (worker) ignore `preferred_channel`. `recommend.py:79` does honour it, so the two disagree.

### D-05 — High — an edited draft is sent without any opt-out text (S2-F04)
- **Test:** `S:test_qa_s2_f04_edited_draft_is_sent_with_opt_out_text`
- **Steps:** `PATCH /drafts/{id} {"body":"Hi there, quick reminder about quotation Q-…"}`, then send.
- **Expected:** the delivered body contains the opt-out instruction (the implementer report says it is "guaranteed").
- **Actual:** delivered body = `Hi there, quick reminder about quotation Q-2026-00001.`
- **Where:** `ensure_opt_out` is applied only at creation (`service.py:223`); `update_draft` (`:258-260`) and `send_draft` (`:390-396`) do not apply it.

### D-06 — High — placeholders in an edited draft are delivered unrendered (S2-F04)
- **Test:** `S:test_qa_s2_f04_placeholders_in_an_edited_draft_are_rendered_before_delivery`
- **Steps:** `PATCH /drafts/{id} {"body":"Hi {contact_name}, quick reminder about {quote_number}. {opt_out_text}"}` (the editor label says "placeholders in braces are allowed", `components/followup.tsx:108`), then send.
- **Expected:** values are substituted. **Actual:** the customer receives literally `Hi {contact_name}, quick reminder about {quote_number}. {opt_out_text}`.
- **Where:** `service.py:259-260` validates placeholders but never renders them; `:393` sends `draft.body` verbatim.

### D-07 — Medium — consented automation ignores `max_attempts` when follow-ups were sent manually (S2-F02/F05)

- **Where:** `process_due_schedule` (`service.py:595-659`) never re-checks the sent count, `policy.max_attempts` or the recommendation before an auto-send.

### D-08 — Medium — no follow-ups are planned when the quote becomes `sent` through the system's own send (S2-F02)

### D-10 — Medium — quiet-hours and weekend shifting reorders and clusters follow-ups (S2-F02); depends on the date
- **Test:** `S:test_qa_s2_f02_quiet_hours_and_weekends_shift_due_times_in_policy_timezone`. Passed on 2026-11-02; failed on 2026-11-10 (R6).
- **Steps:** policy offsets `[1,2,3,4,5]`, `Asia/Dubai`, quiet 19–08, skip weekends; mark sent on Tue 2026-11-10 at about 20:50 local.
- **Expected:** attempts in order, without collisions. **Actual:** order by due time `[1,2,5,3,4]`; attempts 3 and 4 both at Mon 09:00, attempt 5 at Mon 08:00. Under automation the same contact would get 3 messages within an hour.
- **Where:** `service.py:478-498`. Quiet hours shift to `quiet_hours_end` but weekends shift to `max(quiet_hours_end, 9)` (`:494`), and nothing enforces increasing, non-colliding due times.

### D-11 — Medium — a replayed inbound opt-out message crashes inbound processing (S2-F08)
- **Test:** `I:test_qa_s2_f08_unsubscribe_processing_is_idempotent_per_provider_message`
- **Steps:** `record_inbound` twice with the same provider message (`replayed-1`, "Please unsubscribe me").
- **Expected:** idempotent. **Actual:** `psycopg.errors.UniqueViolation … uq_comm_event_provider_msg`.
- **Where:** the idempotency lookup filters `kind == "reply_received"` only (`service.py:665-674`), so `opt_out` events are re-inserted.
- **Inference (not tested with a real provider):** `sync_inbound` advances the cursor only after the whole batch succeeds (`:761-765`), so one replayed opt-out would make every later sync fail.

## Observations (no failing test)
- **O-1 (Low):** `queue.backoff(n)` raises `OverflowError` for n > 42, because the uncapped power is computed before `min()` (`queue.py:28`). It cannot be reached with the default `max_attempts=5`, but `enqueue(max_attempts=…)` is unbounded.
- **O-2 (Low, privacy):** provider error strings are stored verbatim in `job_runs.last_error` and `communication_drafts.last_error` and shown in the admin UI (`queue.py:170`, `service.py:375, 402`). Providers often put the recipient address in 5xx text. Logs stay redacted (S2-A08 passes); the database and UI do not.
- **O-3 (Info):** the dev-only `POST /integrations/simulator/inbound` does not validate `from_email` (an unlinked event is recorded).
- **O-4 (Info, UX):** a schedule's cancellation reason and actor are kept in audit only; the follow-ups table shows the planning reason.
- **O-5 (test quality):** the implementer's `tests/e2e/specs/stage2-followup.spec.ts:78` opts out `getByTestId("opt-out").first()` on the first seeded customer instead of the contact it created, so it fails whenever another spec adds a primary contact to that customer (R7). I changed only my own spec. Recommendation: target the row by e-mail. Also `apps/api/tests/integration/test_stage2_followup.py:466` asserts `… or True`, which can never fail.
- **O-6 (design deviation, documented):** PRD S2-F07 says "Redis-backed"; ADR-012 was amended to a PostgreSQL queue. I verified behaviour against ADR-012.
- **O-7 (scope):** Gmail and Microsoft Graph adapters are not shipped, so S2-F06 is partial and S2-A05 (OAuth token expiry or revocation) cannot be exercised.
- **O-8 (inference, untested):** a rate-limited automated send counts as a failed attempt. The default backoff sums to about 7.5 min (30+60+120+240 s) across 5 attempts, which is less than the 1 h rate window, so at a sustained limit the follow-up would likely be dead-lettered rather than sent later.
