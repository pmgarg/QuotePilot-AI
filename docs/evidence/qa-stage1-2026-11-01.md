## Defects
Severity: Critical / High / Medium / Low. Each defect has a failing test left in place (name given) unless marked “observation”.

### D1 — Expired approved quote is still exportable as the current approved PDF — **High** (S1-A15, S1-F15)
- Where: `apps/api/app/services/exports/quote_exports.py:74` (`render_and_store_pdf` only refuses `quote.status == "withdrawn"`; expiry is never evaluated) and `build_pdf_model` (label stays `APPROVED`).
- Request: approve a quote, let `valid_until` pass (test moves it to yesterday), then `GET /api/v1/quotes/{id}/versions/1/pdf` or `POST …/pdf` as any role.
- Expected: `409 {"error": "invalid_state"}` (acceptance S1-A15: “export-as-current rejected with 409 state error”); `effective_status` is already reported as `expired` by `GET /quotes/{id}`.
- Actual: `200 application/pdf` (GET) and `200 {"sha256": …, "status": "approved"}` (POST); the document is labelled APPROVED with a past validity date and can be sent to a customer.
- Tests: `tests/qa/test_qa_quote_lifecycle.py::test_expired_approved_quote_cannot_be_exported_as_current[GET]` and `[POST]`.

### D2 — Quote withdrawn while pending approval can still be approved or rejected — **High** (S1-F15, S1-F14)
- Where: `apps/api/app/services/quotes.py:588-608` (`withdraw` sets `quote.status = "withdrawn"` but leaves `version.status` at `pending_approval`); `approve` (`:500`) and `reject` (`:556`) check only `version.status`, never `quote.status`.
- Request: submit → `POST /quotes/{id}/withdraw` (approver, reason) → `200 status=withdrawn` → `POST /quotes/{id}/approve` (or `/reject`) with the returned `lock_version`.
- Expected: `409 invalid_state`; quote stays `withdrawn`.
- Actual: `200`; the quote becomes `approved` (resp. `draft` after reject) with an `approved` decision appended after the `withdrawn` decision, i.e. a withdrawn quotation is silently revived. (`submit` is correctly refused because it checks `effective_status`.)
- Tests: `test_withdrawn_pending_quote_cannot_change_state[approve]`, `[reject]` (`[submit]` passes).

### D3 — Withdrawn (and expired) approved versions remain exportable as CSV — **Medium** (S1-F15)
- Where: `apps/api/app/services/exports/quote_exports.py:100` (`render_csv` has no state check at all, unlike the PDF path).
- Request: approve → withdraw → `GET /quotes/{id}/versions/1/csv`.
- Expected: `409 invalid_state` (same rule as the PDF, which already returns 409 for withdrawn).
- Actual: `200 text/csv` with the full priced lines and no indication of withdrawal.
- Test: `test_withdrawn_approved_quote_cannot_be_exported_as_csv_current`.

### D4 — Audited margin override is silently dropped by any “Save draft” that does not change the price — **Medium** (S1-F12, S1-F13)
- Where: `apps/api/app/services/quotes.py:426` clears `margin_override_reason/by` whenever the payload merely *contains* `unit_price`, `discount_pct` or `product_id`, without comparing values; the web editor `apps/web/src/app/(app)/quotes/[id]/page.tsx:78-90` (`save()`) always re-sends every field of every line. Net effect: after an Owner/Admin override, the next save by Sales (e.g. editing notes or terms in the UI) removes the override, the `below_min_margin` blocker returns and the audit trail shows no corresponding event.
- Request: override line → `PATCH /quotes/{id}` with the unchanged line (`unit_price: "0.55"`, `discount_pct: "0"`) and `notes`.
- Expected: `margin_override_reason` retained, `blockers == []` (a true price/discount/product change should still clear it — that behaviour is verified and passes in `test_margin_override_cleared_after_price_edit`).
- Actual: `margin_override_reason: null`, blocker `below_min_margin` back, no audit row for the removal.
- Test: `test_margin_override_survives_save_with_unchanged_price` (the notes-only variant passes, proving the API is fine when the client omits the lines).

### D5 — Last *active* owner can be deactivated; organisation left without any active owner — **High** (S1-F01)
- Where: `apps/api/app/api/routers/org.py:119-136` — `owners` counts all owner memberships regardless of `users.is_active`; the guard at `:136` therefore passes once a second (already deactivated) owner exists. Additionally an Admin may deactivate an Owner at all (role changes of owners are owner-only at `:129`, deactivation is not).
- Request: owner creates `owner2` → owner deactivates `owner2` (200, legitimate) → **admin** `PATCH /org/members/{owner1}` `{"is_active": false}`.
- Expected: `409 conflict` (“last owner”); at least one active owner remains.
- Actual: `200` with `user.is_active: false`; the org has zero active owners, so owner-only actions (enable self-approval, grant owner role) become impossible and an Admin has effectively locked out ownership.
- Test: `test_last_active_owner_guard_counts_only_active_owners`.

### D6 — `POST /auth/logout` is accepted without a CSRF token — **Low** (S1-F02, `docs/API_CONTRACT.md` “Unsafe methods require header X-CSRF-Token”)
- Where: `apps/api/app/api/routers/auth.py:93-98` depends on `current_session` only, bypassing `csrf_protect`.
- Request: authenticated session, `POST /api/v1/auth/logout` without `X-CSRF-Token`.
- Expected: `403 forbidden action=csrf`; session intact.
- Actual: `200 {"status":"logged_out"}`; a cross-site page can force-logout users (nuisance only; no data exposure).
- Test: `test_logout_requires_csrf_token`.

### D7 — Out-of-range quantity on RFQ items returns 500 instead of 422 — **Medium** (S1-A09, robustness)
- Where: `apps/api/app/schemas/common.py:235` (`RFQItemUpdate.quantity: Decimal | None`, no bounds) and `:246` (`RFQItemCreate.quantity`, `gt=0` only) versus `QuoteLineIn.quantity` at `:256` which has `le=1e9`; the value reaches `Numeric(18,3)` in `apps/api/app/services/rfqs.py:409`/`:480` and PostgreSQL raises `NumericValueOutOfRange`, surfacing as `500 internal_error` (logged as “unhandled error”).
- Request: `PATCH /rfqs/{id}/items/{item}` `{"quantity": "1e400"}` or `"99999999999999999999"`; same for `POST /rfqs/{id}/items`.
- Expected: `422 validation_error` naming `quantity`.
- Actual: `500 {"error":"internal_error"}`.
- Tests: `test_patch_item_rejects_invalid_quantity[1e400]`, `[99999999999999999999]`, `test_add_item_rejects_out_of_range_quantity[1e400]`, `[99999999999999999999]`.

### D8 — Pasted line starting with `-5 pcs …` is parsed as quantity 5 with no flag — **Low** (S1-A09, “never invent facts”)
- Where: `apps/api/app/services/parsing/extract.py:213 ff.` (`items_from_text_lines` strips a leading `-` as a bullet marker before reading the quantity).
- Request: `POST /rfqs` `{"text": "-5 pcs SKU-1002 Hex bolt M8x60\n"}`.
- Expected: `quantity: null` with a `quantity_*` flag (as the CSV path does for `-5`), or at minimum a flag so the reviewer sees the sign was discarded.
- Actual: `quantity: "5"`, `flags: []`, status `exact` → a negative/withdrawn line turns into a priced positive quantity without any review hint. The implementer’s own test tolerates either outcome; QA regards the silent sign drop as a (low) data-integrity defect since “- 5 pcs” (bullet + space) and “-5 pcs” are distinguishable.
- Test: `test_leading_minus_quantity_in_pasted_text_is_not_silently_made_positive`.

### Observations (no failing test; for product/implementer decision)
- **O1** Admin may deactivate a non-last Owner (`org.py:136` only guards the last owner) although Admin may not change an Owner’s role; the role matrix does not state a hierarchy, so this is recorded, not failed.
- **O2** With more than one catalog, `active_version_for_org` (`catalog_import.py:375`) always uses the oldest catalog’s active version; a second catalog’s activation is accepted (and audited) but never used for matching. No requirement covers multi-catalog, so recorded only (QA test for S1-A19 was adjusted to use a second *version* of the same catalog).
- **O3** S1-A03 says a custom line gets an explicit price “(privileged)”; the implementation lets any editing role (Sales included) enter a manual price with `price_source: manual` and no reason. S1-F11 (“explicitly entered”) supports the implementation; S1-A03 and S1-F12 suggest a privileged, reasoned step. Needs a product decision; both behaviours are documented by tests (`test_currency_mismatch_blocks_autofill` existing; `test_unknown_item_custom_line_requires_explicit_price` added).
- **O4** Pasted text > 200 000 characters is refused by the Pydantic `max_length` with `422` (`schemas/common.py:226`) while 100 001–200 000 characters give the intended `413`; the limit message is only shown in the 413 case. Harmless but inconsistent with S1-A08 (“413 with limits stated”).
- **O5** `rfq.generate_quote` has no audit action of its own (covered by `quote.create` carrying `rfq_id`); acceptable under S1-F18 and verified.

- No Docker daemon: `docker compose` topology, `make db-up` and the container-based demo were not exercised (local PostgreSQL service used instead).
- Scanned-PDF OCR, hosted AI provider (`AI_PROVIDER=anthropic`), S3 storage adapter, SMTP: disabled by configuration; only the `disabled` adapter and local storage were under test (no paid resources, no network).
- Parser wall-clock timeout and memory limit were exercised at unit level by the existing sandbox test and at integration level by stubbing `run_parser` (D-free); a genuine multi-second hang inside the subprocess was not provoked to keep the suite fast.
- Login rate limiting is in-process (single replica); verified per process only.
- Catalog row cap (`max_catalog_rows = 50 000`) and PDF page cap (`max_pdf_pages = 50`) were not exercised with real oversized fixtures (would require generating multi-MB files; the 10 MiB byte cap and zip-bomb guard are covered).
- Accessibility (WCAG AA, keyboard operability) was not audited; the browser tests assert states and role-aware rendering only.
- `tests/e2e/specs/screenshots.spec.ts` (added in commit `7a29d68`) self-skips; it is a walkthrough capture, not a test, and was left untouched.
